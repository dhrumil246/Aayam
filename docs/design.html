Design document

Twin-Ticket Task Factory

Design as of 23 Nov 2026Target repo: pallets/clickSubmission due 6 Dec 2026Team of 4

We turn a real repository into new, runnable feature tasks. The factory generates them in twins: two standalone tickets from the same commit that differ in one meaningful rule. It then finds the exact case a grader must check to tell the two apart.

1Intent

Build a reusable factory that turns a real repository into new, runnable feature-development tasks, and prove the tasks are good. Twins supply evidence for three scored criteria at once:

  • Validity: the tests demonstrably reject a plausible wrong implementation (the twin).
  • Variation: the difference is behavioural and proven by execution, not by wording.
  • Impact: twins measure whether an AI solver actually follows the requirement that changed.

Pitch line: "Our factory generated two individually solvable tasks and found the test needed to tell them apart."

3Goals, non-goals, anti-goals

Goals
  • One command generates and validates a twin pair from a pinned click commit.
  • Every package passes the basic validation matrix.
  • 8–12 validated pairs (16–24 packages) across at least 5 behaviour families.
  • An evidence report a reviewer can open without any API key.
  • A live demo: generate, validate, cross-grade, break the grader.
Non-goals
  • Supporting all three repos. A second repo is a bonus only if everything else is green by 3 Dec.
  • A polished web app. A CLI plus a small demo page is enough.
  • Training data at scale.
  • Adaptive follow-up generation for the first deadline. It's a later stretch goal.
Anti-goals
  • Tasks that differ only in names, wording or literal values.
  • Tests that import private internals.
  • Tests that check behaviour the ticket never states.
  • Features that already exist upstream.
  • Testable features no real user would want.
  • Evidence that only reproduces with paid API calls.

4Constraints

  • 13 days (24 Nov – 6 Dec), 4 people, standard laptops.
  • Model access through provided model credits (provider and amount to be confirmed). Every model call goes through one function, so the provider is a config value.
  • No API keys in the repo. Reused open source is listed in the README.
  • Native stack: tasks run in click's own Python and pytest setup.

5Approaches considered

ApproachTrade-offVerdict
A. Reverse SWE-smith: delete an existing feature, ask for it backCheap; existing tests give validity. Not new, likely in training data, weak originality.Rejected
B. Mine upstream feature PRs (FEA-Bench / SWE-Dev style)Realistic, but contaminated, not generation, and copies prior work.Rejected
C. Novel feature synthesis with an adversarial validation gauntletOriginal and strong on validity. On its own, variation is asserted rather than proven.Merged
D. Twin tickets, small-difference search, break-the-grader demoProves variation and requirement sensitivity; great demo. Its hand-built behaviour model was a scope risk, and two references can share a bug.Merged
C + DTwins are the product, the pivot probe and differential search are the engineering centrepiece, the gauntlet is the proof, break-the-grader is the demo. Costs twice the generation per feature and more gates.Chosen

Changes made while merging:

  • No hand-built behaviour model. Search runs on the two real patched copies of click.
  • Expected outcomes come from the tickets, never from a reference's output (§8).
  • The mutant gauntlet is mandatory, because two LLM references can share the same bug.
  • Breadth across behaviour families is mandatory, so twins don't all look like one template.

Repo: pallets/click. Python has the best tooling (pytest, Hypothesis, mutmut) and the most reliable LLM patches. A CLI invocation is naturally a sequence of actions, so break-the-grader maps cleanly. zod is the fallback; jsoncpp is avoided (slow builds, poor mutation tooling).

6Core concepts

Seed featureOne repo-grounded feature idea tied to an existing extension point, such as option declaration, parameter source resolution or chained command results.
Policy dimensionThe one decision inside the feature where two reasonable rules exist. Each rule has a stakeholder reason for why a real team would pick it.
ContractNumbered, testable requirements R1…Rn. Shared clauses are identical across twins; exactly one clause, the pivot clause, differs. The contract also lists what is deliberately left open.
TicketThe public brief in Markdown that a solver sees. Derived from the contract; never includes hidden tests or the twin.
GraderThe hidden feature tests for one ticket. Each test is tagged new or preserved and cites the requirements it checks.
Pivot probeAn input that exercises the changed rule, plus each ticket's expected outcome written as semantic assertions.
PackageOne standalone task: ticket, base commit, reference patch, grader and evidence. Twins are two packages linked by pair_id.

8Validation gauntlet

Every run happens in Docker from a clean checkout of the base commit plus the patch under test.

GateCheckPass condition
G0 BaselineExisting suite on baseGreen; known flaky tests listed and excluded the same way everywhere
G1 Fail-beforeGrader on base; tests tagged new or preservedEvery new test fails for an expected reason: an assertion failure, or the missing public API named in the contract. Collection errors, import errors in the test file or broken fixtures never count. preserved tests pass on base.
G2 Pass-afterGrader plus full existing suite on the referenceAll pass
G3 StabilityG1 and G2 repeated 5 timesIdentical results
G4 Public-API lintAST scan of grader imports and attribute accessNo private names, no reference-only helpers
G5 Twin separationPivot probe from the tickets, replayed through both real patches, then cross-gradeEach reference meets its own ticket's pivot assertions and violates its twin's; both graders contain the probe
G6 Mutant killAt least one plausible wrong patch per requirement, violating exactly that requirement; mutmut on changed lines as a bonusEvery requirement has a killed mutant; survivors are argued equivalent (logged) or trigger test repair

Pivot probe and differential search (G5)

RuleTwo patches disagreeing only proves they differ. Expected outcomes always come from the frozen tickets, never from a reference's output.

Example: ticket A says "report the first invalid value", ticket B says "report all invalid values". If the patches also differ in punctuation, naive differential search finds and tests the punctuation. The cross-grade looks perfect while neither grader checks two invalid values. So G5 needs three things:

  1. A pivot probe: an input that exercises the changed rule (here, two invalid values in a known order). Written in the contract stage with the feature's input grammar.
  2. Ticket-derived expectations: for each ticket, a separate model call that sees only that ticket and the probe writes the expected outcome as semantic assertions. A: only the first invalid value is reported. B: both are, in order. Anything the ticket leaves open, such as wording or punctuation, stays unasserted.
  3. Replay through both real patched copies of click: show what each reported, confirm A meets A's assertions and fails B's and vice versa, then export the assertions as tests into both graders.

Differential search then acts as a lead finder, not an oracle:

  • Each reference gets its own worktree and a worker process that reads {argv, env, input} JSON lines and returns {exit_code, output, exception_type} via click.testing.CliRunner. Hypothesis generates invocations from the grammar and sends each to both.
  • Hypothesis shrinks a disagreement to a small example (not guaranteed shortest). The example is classified against the tickets:
    • On the pivot a candidate extra probe, with expectations again written from the tickets;
    • On a shared clause one reference breaks the shared contract, a bug to repair;
    • Left open by the tickets: ignored and logged.
  • Every saved case is replayed in fresh processes before it counts, to rule out state leaking between workers.
  • If the budget runs out with no pivot difference, record "no distinguishing case found within budget" and reject the pair.
  • The demo button reads "Find a small difference".

Three-way diagnosis (stage 7)

When the blind solver's patch fails a grader:

  1. Differential search between the solver patch and the reference gives a small disagreeing input.
  2. An AI judge sees only the ticket, that input and both outputs, and answers whether the ticket determines the correct output.
  3. Classify:
    • Solver mistake The ticket determines the output and the solver is wrong. The task stays as is.
    • Grader mistake The ticket allows the solver's behaviour. Fix or relax the test and re-run the gauntlet.
    • Ambiguous ticket The ticket doesn't decide it. Offer two fixes: add the missing clause, or accept either outcome. Never silently invent a rule.
  4. Verdicts are logged with the counterexample; showcase pairs get a human check.

A blind solver that passes is solvability evidence without the reference.

9Variation strategy

Candidate behaviour families for click. Each pair must pass the novelty gate against current click source.

FamilyExample policy pair (verify novelty)
Conflict resolutionMutually exclusive options: error vs last one wins
Source precedenceEnv var vs default vs flag: which wins when combined with a new source
Repetition / accumulationRepeated option: accumulate vs override vs error after N
Validation & errorsReport the first invalid value vs collect all invalid values
Lifecycle / orderingChained subcommand failure: stop the chain vs run the rest and report
Deprecation / compatibilityDeprecated alias: warn and accept vs reject with a hint
Retry / interactionPrompt on invalid input: re-prompt N times vs fail immediately
  • A pair varies one rule. A batch varies families. The final set covers at least 5 families, shown as a coverage grid.
  • A twin pair counts as one feature when claiming variation.
  • Measured: distinct files and functions touched across reference patches; overlap of shared-clause tests between pairs from different families (should be near zero).
  • Cross-grade separation among accepted pairs is 100% by construction, so it is reported as a gate, not a result. The held-out check (G6h) is the result.

10Requirement-sensitivity experiment

Give tickets A and B to a solver model in separate blind runs; neither sees the twin, pair_id or hidden tests. Score in two steps:

  1. Shared requirements: does each patch meet the shared clauses? Failures here are plain failures and drop out of step 2.
  2. Changed rule: run both patches on the pivot probe and score each against its own ticket's assertions.

11Package layout

Provisional until the required package template is final. Each package separates what a solver may see from what only the evaluator sees.

packages/
  click-<family>-<slug>-A/
    task.md              # PUBLIC: the ticket, the only thing a solver gets besides the base repo
    env/
      Dockerfile         # pinned base image digest + locked dependencies
      requirements.lock
    evaluator/           # HIDDEN from solvers
      meta.json          # repo, tag, base SHA, family, pivot clause, pair_id, twin_package, model + cost, gate results
      solution.patch     # reference implementation
      tests/test_feature.py  # grader; tests tagged new/preserved + requirement ids
      regression.txt     # existing-suite command + excluded flaky tests
      replay.sh          # rebuilds env and reproduces every result, no model calls
      patches/
        mutants/         # every G6 mutant
        heldout/         # G6h wrong patches + valid alternative
        solver/          # blind-solver patches per model
      evidence/
        matrix.json  probe.json  mutants.json  heldout.json  trace.json  logs/
  click-<family>-<slug>-B/ ...
pairs/<slug>.json        # links A/B, pivot probe, cross-grade matrix
report/index.html        # static report, opens offline
demo/run_demo.sh         # executable demo command

Acceptance test: a teammate who didn't generate a package runs replay.sh on their own machine with model access disabled and gets identical results. Only fresh generation needs API calls.

12Demo script

  1. "We turn a real repository into new, runnable coding tasks." One command on pinned click. Show the commit, the surface the factory found and the two generated tickets, with the one differing sentence highlighted.
  2. Basic validation matrix: existing tests pass on base, feature tests fail on base, the reference passes both.
  3. The innovation: the viewer reads the changed sentence and predicts the result; the factory replays the pivot probe through both real patched copies and confirms each matches its ticket. Then milestone M1: a wrong patch the initial grader accepted, the case the factory found, and the improved grader rejecting it while a different valid solution still passes.
  4. Break the grader: a viewer types a click invocation and both patched versions run side by side. "Find a small difference" shrinks and replays it in fresh processes, then exports it as a pytest file and runs it.
  5. Fairness: the blind solver's patch and one example of each diagnosis.
  6. A second family: a different kind of rule, to show it isn't one template.
  7. Numbers: packages generated, gate pass and reject rates with reasons, held-out result, mutant kill rate, requirement sensitivity of 2 models, cost per package.
  8. Limitations (§17), stated plainly.

A recorded backup video of the full demo is mandatory.

13Architecture & stack

  • Orchestrator: Python 3.12 CLI: factory generate, validate, export, report. Run state as JSON files per pair; no database.
  • Repo adapter: one file for click covering clone/pin, Docker image, test command, worker harness, public-API rules and discovery hints. A second repo means a second adapter file and nothing else.
  • Sandbox: Docker per run, network off during tests, clean worktree per patch.
  • Model calls: one llm(prompt, model) function, model names in config, token and cost logging on every call, a hard cost cap per pair.
  • Search: Hypothesis for generation and shrinking; one worker process per worktree; fresh-process replay before a case counts.
  • Mutation: requirement-targeted LLM mutants (required), mutmut on changed files (bonus).
  • Demo page: a small Streamlit app over the same functions.
  • Report: static HTML generated from the JSON evidence.

Reused open source, to list in the README: click, pytest, Hypothesis, mutmut, Docker, Streamlit, the model provider's SDK.

16Metrics in the evidence report

  • Pairs attempted, accepted and rejected, with the rejecting gate for each
  • Basic validation matrix per package (all must pass)
  • Held-out result (headline): wrong patches accepted by initial vs final graders; valid alternatives accepted by final graders
  • Pivot probes per pair; small-counterexample length; pairs rejected as "no distinguishing case found within budget"
  • Mutant kill rate per requirement; equivalent mutants with justification
  • Blind-solver pass rate; diagnosis counts (solver, grader, ambiguity)
  • Requirement sensitivity per model
  • Family coverage grid and patch diversity
  • Tokens and cost per accepted package; wall time per stage

17Limitations to state in the write-up

  • One repo validated end to end. Carrying over means writing an adapter, done for one (or two) repos.
  • The AI judge in diagnosis can be wrong. Showcase verdicts are human-checked; the rest are logged as model judgments.
  • Ticket-derived expectations come from a model reading the ticket. They're checked against both references and showcase probes are human-reviewed, but a shared misreading is possible.
  • Differential search only explores the declared input grammar; a difference outside it can be missed. Shrunk examples are small, not guaranteed shortest.
  • LLM mutants approximate real solver mistakes but don't cover them all.
  • Feature realism is partly a judgement call; the rubric and human sign-off reduce that, not remove it.
  • The sensitivity experiment covers few models and pairs. It's a demonstration, not a benchmark result.

19Calls made in this design

  • Starting commit: the provided starter kit is the authority for the base revision, export format and benchmark protocol. If it names a click revision, record and pin it. If not, pin click's latest stable release on 24 Nov.
  • Novelty scope (G8): upstream main (not just our tag), docs, changelog, and open PR/issue titles. Anything that landed after our tag counts as existing.
  • Twins and variation: a twin pair counts as one feature. Variation is claimed from the spread of families and features; twins are validation and sensitivity evidence. A and B stay standalone packages.
  • Twin link survives any template: each package's meta.json carries pair_id, twin_package and pivot_clause, kept out of the solver's view.
  • Budget fallbacks, in cut order: (1) drop mutmut, keep LLM mutants; (2) sensitivity experiment on one model; (3) blind solver on the same model as the references, with a fresh context and only the ticket; (4) cut the target to 6 pairs.
